# Tools and connectors: repository, CI, issues, MCP, and grounding

Part of Harness 2.0 (second round, 2026-11-23). Client plugins
`plugins/repo` and `plugins/grounding`; MCP completes the planned P3
(`WORKSPACE_PANEL_SKILLS_PLUGINS.md` §5). Switches `KRIYA_REPO_TOOLS`,
`KRIYA_GROUNDING`, `KRIYA_MCP` (all default off).

## 1. Where credentials live (the rule that shapes everything here)

| Credential | Lives | Kriya ever sees it? |
| --- | --- | --- |
| The person's GitHub/GitLab login on their machine | Their `gh` / `glab` / git credential helper | **No.** The harness runs those programs; it never reads their config, never calls `gh auth token`, never prints an `Authorization` header |
| OAuth tokens of Kriya's connected accounts | Sealed in `kriya.connections`, opened only in `lib/connectors.ts` (invariant 4) | Server only, for cloud agents and track C. **Never sent to a device**, and the harness API never runs a connector (track H rule 6) |
| MCP server tokens (registry servers) | Sealed in `kriya.mcp_connections` (track N rule 7) | Server only; the device gets a server only after P3a's delivery design, never a token (§4) |
| Deploy provider logins | The provider's own CLI on the machine | No (DELIVERY_AND_STABILITY §3) |

So on the person's machine, "connect to GitHub" means "the harness can use
the GitHub CLI you're already signed in to", with every outward action
approved by you. Signing in is yours: if `gh auth status` exits non-zero
the harness says "Run `gh auth login` in a terminal", and the agent never
types a credential (track-A rule 4, R5).

## 2. Typed repository tools (`plugins/repo`)

Raw shell can already run `git` and `gh`. Typed tools exist because they
can be **classified, validated and shown precisely in an approval card**,
and because a cheap model calls a well-shaped tool far more reliably than it
composes CLI flags (RESEARCH R-14, the agent–computer-interface finding).

| Tool | Runs (fixed argv, `execFile`) | Class / DSH kind | Rules enforced by code |
| --- | --- | --- | --- |
| `repo_status` | `git status --porcelain=v2 --branch`, `git remote -v` (host/path only, credentials stripped as `src/overview.js` does) | read | — |
| `repo_diff` | `git diff [--staged] -- <paths>` | read | ≤ 60 KB, then a file list |
| `repo_log` | `git log --oneline -n ≤ 50` | read | — |
| `repo_branch` | `git switch -c kriya/<slug>` | **approval in every mode** (Auto refuses) | Name `kriya/[a-z0-9-]{3,50}`; refused with uncommitted changes that would be carried silently |
| `repo_commit` | `git add -- <paths>` then `git commit -m <msg>` | **approval in every mode** (Auto refuses) | Paths must be files this session changed (from its checkpoints); never `.env*` except `.env.example`; message must be a Conventional Commit ≤ 72 chars subject; refused in Read only |
| `repo_push` | `git push -u origin kriya/<slug>` | **outward** | Only `kriya/*` branches; never `--force`; never the default branch; G-SECRETS over the whole outgoing range (`git diff <merge-base>..HEAD`) must pass first; Ask mode asks with the exact branch and commit list; Auto refuses (HD-20) |
| `pr_create` | `gh pr create --draft --base <default> --head kriya/<slug> --title <t> --body-file <tmp>` | **outward** | Draft only; the body starts with the **proof receipt** generated by code (DIFFERENTIATORS §1), the model's summary after it under "Agent's notes"; approval as above |
| `pr_view`, `pr_checks` | `gh pr view --json …`, `gh pr checks --json …` | read | Output is untrusted (`FOREIGN`): it can contain other people's text |
| `ci_logs` | `gh run view <id> --log-failed` | read | ≤ 20 KB of failing lines; untrusted; secrets-masked by GitHub, and G-SECRETS' patterns redacted again before the model sees it |
| `issue_read` | `gh issue view <n> --json title,body,labels,comments` | read | Untrusted; comments truncated |

**Why local commits also need approval.** Until now the harness never
moved HEAD, a branch or the index (checkpoints live on `refs/kriya/*`;
`KRIYA_LOOP_V2.md` §4), and two checks rely on HEAD as "the code before
this session": v2's originals re-run (`onOriginals`, `src/verify.js:261`,
reads `HEAD:<path>`) and the strict loop's test-weakening and syntax
checks. A builder that could commit would make its weakened tests the new
"originals". So: with repository tools on, every such read uses the plan's
recorded `base` commit instead of `HEAD` (one optional argument, default
`"HEAD"`, so behaviour without repository tools is unchanged), and branch
and commit run only on the person's approval.

Not tools, by design: merge, close, delete branch, force push, edit someone
else's PR, comment on issues, release, tag. A person does those (track C
rule 6's principle: the agent proposes changes, it never merges).

**CI loop.** After `pr_create`, `pr_checks` is polled by **code** (no model,
no spend) every 30 s for up to 20 minutes. A failing check becomes a
proposed new plan step "Fix CI: <check name>" with the failing log excerpt;
the head plans it only if the person says yes. Green checks are shown as
evidence in the receipt, labelled "reported by GitHub".

GitLab: the same tool shapes over `glab` in a later phase; nothing in the
interface is GitHub-specific except the CLI adapter.

## 3. Connect a project to a repository

In the Overview tab (exists, P1) the repository row gains states, each with
one next action, all computed from read-only `git`/`gh` calls:

| State | Shown | Action offered |
| --- | --- | --- |
| Not a git repository | "Not under version control" | `git init` (local, approval) |
| No remote | "Not connected to a remote" | "Create on GitHub" → `gh repo create <name> --private --source . --remote origin` (outward, approval, private by default) |
| Remote, `gh` signed out | Remote host/path | "Sign in with `gh auth login`" (the person runs it) |
| Remote, signed in | Host/path, branch, ahead/behind, open PR for this branch, its checks | Push / open draft PR (approval) |
| Linked to a Kriya workspace (H8) | Workspace name | Hand off / pull (existing) |

`.gitignore` check on connect: if `.env`, `.env.local` or `*.pem` would be
tracked, the harness says so and offers the ignore lines (a local edit the
person approves).

## 4. MCP: finishing P3 with the owner's registry

The design in `WORKSPACE_PANEL_SKILLS_PLUGINS.md` §5 stands (P3a registry
servers behind `KRIYA_MCP`; P3b person-added servers behind
`KRIYA_MCP_OWN`, which needs the AGENTS.md amendment quoted there). What
Harness 2.0 adds:

1. **Delivery of registry servers to a device without a token.** A
   registry server is delivered as `{ name, url, toolsHash }` only for
   servers whose auth the person completes **on the device** (OAuth in
   their browser against the provider, token stored by DSH's MCP client in
   the device's own credential store) or that need none. Servers whose
   tokens live sealed on Kriya's server stay cloud-only, because a device
   may not receive them (track H rule 6, invariant 4). Spike W15 S1: confirm
   how `dsh-mcp-client` stores Streamable-HTTP OAuth tokens and that its
   store is outside the project folder.
2. **Pinned definitions.** On connect, the client hashes each tool's full
   definition and compares it with the registry's `toolsHash`; a drifted
   tool is not registered (track N rule 4's behaviour, on the device).
3. **Classification.** Tools are classified from the registry entry's
   owner floor (track N rule 5 reasoning); anything not read-only is
   `execute` in DSH, so Ask mode asks and Auto refuses.
4. **Candidate registry entries for the owner to review** (each needs the
   owner's review of the provider's own documentation, licence and auth
   model before it is added; none is asserted here): GitHub's MCP server,
   an issue tracker (Linear or Jira), error tracking (Sentry), design
   handoff (Figma's local Dev Mode server), the person's database provider
   (Supabase), a version-aware documentation server.

## 5. Grounding: the cheap-model multiplier (`plugins/grounding`)

Cheap models fail most often on **facts about the code they're calling**:
an API that moved in the version installed, a prop that doesn't exist, a
config key from an older major. The fix is to answer those facts from the
project's own installed files, which are exact for the installed version,
local, free and deterministic.

| Tool | Answers | From | Bounds |
| --- | --- | --- | --- |
| `api_lookup { package, symbol }` | The exported signature(s) and doc comment of `symbol` | The installed package's type definitions: `package.json` `types`/`typings`/`exports[*].types`, then `@types/<pkg>`; Python: `*.pyi` stubs, else the `def`/`class` lines of the installed source found by text search. Nothing is imported or executed: importing a module runs its code | ≤ 8 KB; symbol search by exact name, then prefix |
| `api_changes { package }` | What changed between the version the code was written for and the installed one | The installed package's `CHANGELOG.md`/`HISTORY.md` sections between the two versions (`package-lock`/`pnpm-lock` history at HEAD vs now) | ≤ 8 KB; "no changelog shipped" otherwise |
| `api_version { package }` | Installed and declared versions | Lockfile + `node_modules/<pkg>/package.json` | — |

- Builders of steps whose files import a package get a one-line hint naming
  `api_lookup` (late prompt section, so the cached prefix is unchanged).
- With grounding on, the strict loop's existing `types` rung (`tsc
  --noEmit`, `src/strict.js`) already turns a hallucinated API into a type
  failure with an excerpt; grounding makes the next attempt fix it from a
  fact instead of another guess.
- No network: this is the version-exact answer. Web documentation, when
  needed, comes only through an owner-reviewed MCP docs server (§4).

## 6. Security summary

- Every outward action (push, PR, repo create) is an approval with the
  exact target shown; Auto mode refuses them; Read only runs none.
- Output from GitHub, CI, issues and MCP is untrusted and private: marked
  `FOREIGN`, never turned into rules or memory without the person.
- No tool reads credential stores, `~/.config/gh`, `.git/config` credentials
  or environment secrets; repository URLs are shown as host/path only.
- G-SECRETS guards every push.
