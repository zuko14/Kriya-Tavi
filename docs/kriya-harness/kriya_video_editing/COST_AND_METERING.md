# Cost and metering (track E)

## 1. Who pays for what

| Cost | Paid by | Recorded in |
| --- | --- | --- |
| Compute: indexing, rendering, models that run locally | The person's own machine | Journal, for their information only |
| Model tokens | The person's plan, with its markup | `kriya.harness_usage`, unchanged |
| Preview storage | Kriya, inside a plan cap | `kriya.resource_usage` kind `edit_preview_bytes` |
| Runtime downloads | Hosted by each upstream or by Kriya (EDD-05) | Owner's bill if Kriya hosts them |

No new ledger. `lib/agent/metering.ts` and `kriya.charges` are not touched
(invariant 6, track H rule 4). Local work has no price, so "Zero Cloud Render
Tax" in the brief is simply true by design.

## 3. What a job can cost at its cap

Arithmetic on the budgets in DIRECTOR_AND_AGENT §13, at Flash-1017's list prices,
before Kriya's markup. A cap is a worst case, not a forecast.

| Job | Input cap | Output cap | At the cap |
| --- | --- | --- | --- |
| Short form | 300 k | 40 k | 300 k × $0.15/M + 40 k × $0.60/M = $0.045 + $0.024 = **$0.069** |
| Long form | 3 M | 300 k | $0.45 + $0.18 = **$0.63** |

The same token counts on Opus 5.5 would be $2.00 and $18.00. But a free agent
loop doesn't use the same token counts: ghost-editor reports 212 M cached tokens
re-read to build 3 reels. At Opus 5.5's listed cached rate that volume alone
would be 212 × $0.20 = $42.40, though that run was on a Claude plan, not metered
API prices, and on an unstated model. It's here to show what turns cost, and
nothing more.

Rupee figures aren't shown here: the charge uses the owner's `fx.usdInr` and the
plan's markup at run time. No exchange rate is invented.

## 4. Where cost really goes, and what controls it

| Driver | Control |
| --- | --- |
| Context re-read each turn | Stateless calls (DIRECTOR_AND_AGENT §5) |
| Output tokens | Typed operations; ids, not prose |
| Reading long transcripts | Story tree: read once, in parallel, cached forever |
| Re-doing work after a change | Revisions touch one slot |
| Images | Few contact sheets, on demand. The gateway reserves a fixed 4,096 tokens per inline image (HT-GW-11); real image token counts are unknown until EX-08 |
| Repair loops | Rung 0 and 1 use no model; three rounds at most |
| Escalation | Rare, decided by code, and refused near the budget |
| Candidates | Capped per recipe; generated by code where possible; ranked low on the fidelity ladder |
| Batching | Many slots per call under the Governor (EDIT_LOOP §8) |
| A prompt cache | Stable prefix. Unproven through the gateway so far (`next.promptCache`, ND-16); no number here relies on it |

## 5. Controls

| Control | Where enforced |
| --- | --- |
| Plan's harness cap (`harness_monthly_micro_inr`) | `reserve_harness_spend`, SQL, as today |
| Tier allow-list | Gateway |
| Per-job budgets | Client code. A convenience for the person, since the true limit is in SQL |
| `plans.editing_preview_bytes` (0 = none) | `kriya.reserve_edit_preview`, SQL |
| `editing.previewMaxBytes`, `editing.previewDays` | Upload route and SQL; janitor |
| `editing.dailyJobs` | `queueEdit()`, by SQL count |

## 6. What the person sees

Every report shows that edit's model cost, from the gateway's answers, with
unpriced calls counted as unpriced, never zero. The Studio shows spend for the
project so far. The `/usage` page shows harness spend as it does today; editing
doesn't get a separate line unless the owner asks (EDD-26).

## 7. Storage

A preview stays under 45 MiB (`editing.previewMaxBytes`), below the platform's
default 50 MiB object limit (EH-23). With an expiry of 14 days and a plan cap,
storage per person is bounded by the cap. The owner sets caps
from Supabase's storage price, read on the day. No price is assumed here.
