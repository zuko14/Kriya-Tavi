## 2. Technique decisions

Facts F1–F5 are the verified facts in the brief. "Off" means behind a `harness.*` switch that defaults off (track H rule 2).

| 1 | Turn/step budget + stagnation stop | Unbounded turns (F1) burn money and loop | R-01 (no budget, rc.5 and master); R-42 (500 iterations + 5 stuck patterns); R-27 ($4 cap → auto-submit); R-43 (opt-in caps); R-03 (vendor evals cap 500 steps); R-37 lists step repetition and premature termination as failure classes | Count steps and reserved spend per turn in an `agent/pre-step` listener; reject or cancel at the cap. ## 3. Benchmark methodology notes

**What the sources say**

- **Run counts.** Terminal-Bench 2.0 used at least 5 trials per model–agent pair (32,155 in total) and reports 95% CIs of about ±3 pp on 89 tasks (R-37). DeepSeek used N=8 (DeepSWE) and N=3 (TB2.1) and published no CIs (R-03). OpenAI's ARC-AGI-3 post gave no run count and no per-setting ablation (R-10). Anthropic: one pass is not a rate; use multiple trials and pass^k for consistency (R-20).
- **Noise floor.** Resource configuration alone moved TB2.0 by 6 pp. On large suites, naive binomial CIs already span 1–2 pp, and gaps under 3 pp are suspect without matched infrastructure. Run on several days (R-21). Miller: report SEs, cluster related items, resample K times per item, compare *paired* per-item differences, and plan sample size with a power analysis. Lowering temperature is not a fix (R-48).
- **Task validity beats task count.** SWE-bench Verified: ≥59.4% of an audited failing subset had flawed tests (R-12). SWE-Bench Pro: 27–34% broken, and the recommendation was retracted (R-11). DeepSWE verifiers disagreed with a judge on 1.4% of runs vs 32.4% for Pro's tests (R-38). A 0% pass rate over many trials usually means a broken task (R-20). Fixing graders and scaffolds took one CORE-Bench result from 42% to 95% (R-20).
- **Contamination.** Public-repo benchmarks leak into training data (R-12, R-39). Original, never-upstreamed tasks are the defence (R-38). Agents read leftover git history across trials, so isolate each trial (R-20). The SWE-Bench Pro containers shipped full `.git` history (secondary, via R-11 coverage).
- **Harness vs model.** Harness effects are large and model-specific: Gemini 2.5 Pro spans 15.7–32.6% across four harnesses, and the best harness differs per model (R-37). The same DeepSeek model spans 65.5–74.2 on DeepSWE across scaffolds, and the minimal ones win (R-03). A result applies to a (model snapshot, harness, config, infrastructure) tuple, not to "the harness".
- **Cost.** Report cost with accuracy (R-49). Token use across harnesses on one model reportedly varies ~7× (R-61, UNVERIFIED).
- **Starting size.** 20–50 tasks drawn from real failures is enough to begin (R-20). Anthropic started its research eval with ~20 queries (R-17). DeltaSelect-style subset selection is preprint-grade (R-50).

**Implications for KriyaBench (F5)**

1. **Pin the snapshot.** Kriya's budget tier is `deepseek/deepseek-v4.1-flash-1017` (`lib/config.ts:465`). DeepSeek moved its `deepseek-flash` alias to the 1017 build on 2026-10-17 (R-04, secondary for the alias). Results from before that date may be a different model. Record the resolved upstream model id per run, and never run evals through an alias.
2. **Retire saturated sets to regression.** 12/12 on easy and 11–12/12 on hard carries no capability signal (R-20). Keep them as a near-100% regression gate.
3. **Build a capability set aimed at a 30–60% baseline pass rate.** Use original tasks (no public fix exists), each with a hidden verify command, a reference solution, and a check that the oracle passes and an empty patch fails. Hand-audit every task, and add an "exploit" run (an agent tries to pass without solving) per R-37.
4. **Runs and statistics.** Use paired design (same tasks, both arms, interleaved in time), K runs per task per arm, and analyse the per-task mean difference (paired t-test or sign test, or a paired bootstrap CI). The table below is a local simulation, not a source result. It shows the minimum detectable effect (pp, 80% power, two-sided α=0.05). It assumes bimodal task difficulty (Beta(0.6, 0.6), mean 0.5) and a uniform additive effect, which is optimistic: real effects cluster on a few tasks.

   | tasks | K=1 | K=3 | K=5 |
   |---|---|---|---|
   | 30 | 33 | 19 | 14 |
   | 60 | 24 | 14 | 10 |
   | 100 | 18 | 10 | 8 |
   | 200 | 13 | 7 | 5 |

   For example, a 30-task suite at K=3 detects only differences of about 19 pp or more, and a single run per arm detects about 33 pp. Decide the effect you care about first, then size the suite. For ~5 pp effects, n=200 at K=5 is the floor.
5. **Report, per arm:** pass rate with a 95% CI; pass^K (all-K success) as reliability; median and p90 cost per task in micro-USD from `kriya.harness_usage`; steps; tokens; cache-hit ratio; and the counts of infra errors and budget stops, kept separate from model failures. Keep infra errors out of the denominator only if they are logged and below ~2% (R-21).
6. **Attribution.** Every eval includes the DSH `sdk-minimal` control arm (technique #20). Change one variable per arm. Fix the container CPU/RAM and declare it (R-21; R-03's harness patch caps test-runner concurrency because `nproc` reports host cores).
7. **Budget.** At ~$0.30/$1.20 per MTok input/output for 1017 (secondary, R-04 coverage) and a 0.1× cache-read price, a 100-task × 2-arm × K=3 run is 600 task-runs. Estimate from measured tokens per task before running. Don't extrapolate from R-61's figures.

## 4. Contradictions and refinements to the brief's facts

- **F1:** Confirmed, and unchanged on `master`. The README names `agent/turn-stopping` as the extension point. DeepSeek's own evals impose `max_steps=500` from outside (R-03).
- **F2:** Confirmed as a mechanism. Refinement: for the budget tier the risk runs the other way. The real window is 1,048,576 with max completion 393,216 (R-05), and DeepSeek recommends `max_tokens` ≥256K (R-04). So the assumed 262,144/32,768 means early compaction at 163,840 tokens, and possibly truncated output at max effort if 32,768 reaches the wire (UNVERIFIED). Simply declaring 1M would push the compaction trigger to ~838k tokens per request, which is costly and in the context-rot zone (R-26).
- **F3:** Consistent with R-02, which also shows DSH has an `agent/request-error` overflow path and an optional tool-result pruner that Kriya can use once the signal arrives.
- **F5:** Beyond saturation, the "budget tier" label hides a snapshot change on 2026-10-17 (see §3.1).
- **Claim C ("DeepSeek Flash 1047 in DSH beat the same model in OpenCode"):** No social-media source found. "1047" is very likely "1017", the id Kriya uses. The only primary source is DeepSeek's own **September V4.1-Flash** card (R-03): DSH Minimal 72.6 vs OpenCode 65.5 (DeepSWE, N=8) and 90.6 vs 85.0 (TB2.1, N=3). These are vendor-reported, with no CIs or independent reproduction, and DSH Standard's TB2.1 lead over OpenCode (85.8 vs 85.0) is within noise. The 1017 card has no scaffold comparison (R-04). The claim is **UNVERIFIED** for 1017.
